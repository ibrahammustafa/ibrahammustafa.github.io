The RF bench

A working model of the test benches I build and run: a known signal goes in, the device under test sits in a shielded chamber, and instruments measure what comes out. Everything is scripted, so it runs on every build. Click any instrument, then scroll down to operate it.

Instrument 01 · stimulus

Signal generator

A precise transmitter you control. Set the frequency, power and modulation, and the device under test receives exactly that. Run a sensitivity sweep to find the weakest signal the receiver can still decode.

How it's used

  • Receiver sensitivity: step power down until packet errors pass a limit. That level is the spec number.
  • Path calibration: inject a known tone and measure it at the other end, so a lossy cable never looks like a bad device.
  • Interference: add a second signal next to the wanted one to test blocking and coexistence.

Scripted, not clicked

Bench instruments speak SCPI over LAN or USB. Python drives them with PyVISA, which is what the log under the screen shows.

Where I've used it

Apple: Wi-Fi and Bluetooth testing in RF chambers with PoE access points and signal generators.

Instrument 02 · measurement

Spectrum analyzer

Shows signal power across frequency. This is the 2.4 GHz band, where Wi-Fi, Bluetooth and microwave ovens fight for the same air. Turn sources on and off, hover to place a marker, and turn on max hold to watch Bluetooth hop.

02
SA-2400 · Spectrum analyzerSWEEPING
CENTER 2442 MHz · SPAN 84 MHzMKR —
Trace

Reading the screen

  • X axis: frequency. Y axis: power in dBm (every 10 dB is 10× power).
  • Wi-Fi is a wide 20 MHz block. Channels 1, 6 and 11 are the three that don't overlap.
  • Bluetooth is a 1 MHz sliver that hops across 79 channels, 1,600 times a second. Max hold shows the full spread.
  • Noise floor drops as you narrow RBW: you see weaker signals, but sweeps take longer.

Why it matters

When Bluetooth audio stutters only while Wi-Fi is busy, this is where you see why: both radios share one band, often one chip. That's coexistence testing.

Instrument 03 · characterization

Vector network analyzer

A VNA tests the test setup itself: cables, connectors, antennas, attenuators. It sends a sweep in and measures what reflects back (S11) and what makes it through (S21). Pick a part to sweep, then move the marker.

03

In plain words

  • S11 low (more negative) is good: little energy bounces back.
  • S21 near 0 dB is good: the signal gets through.
  • A damaged cable shows ripple and dips. An antenna only "takes" power at the bands it was built for.

Why a test team cares

Every chamber has a path-loss number baked into its limits. If a cable drifts by 3 dB, good devices start failing. Sweeping the path keeps the bench honest.

Instrument 04 · simulated distance

Programmable attenuators

Software-controlled dB steps between the access point and the device. Adding attenuation is the same as walking away, except it's repeatable to 0.25 dB. Sweep it to draw a rate-vs-range curve, or cross-fade two APs to force a roam.

What gets tested this way

  • Throughput at each attenuation step (rate vs range)
  • Connect, disconnect and reconnect at weak signal
  • Roaming between two APs as signal shifts
  • Suspend and resume with Wi-Fi staying up
  • Firmware and driver regressions, build to build

Where I've used it

Chrome OS: a lab of about 1,000 Chromebooks in RF chambers behind programmable attenuators, each driven remotely through a servo board for firmware and Wi-Fi chipset validation.

Google OmniLab: installed attenuators while deploying RF-shielded racks for Roku, RDK and Android TV, and Chromecast testing.

Instrument 05 · network traffic

Ixia traffic generator

The signal generator of networking. An Ixia chassis builds packets in hardware at full line rate, stamps each one, sends it through the switch or router under test, and catches it on the far side. Because it knows exactly what it sent, it can measure every lost, late or out-of-order frame.

How it generates traffic

  • Stream builder: you define headers (MAC, VLAN, IP, UDP/TCP) and let fields increment, so one stream can look like thousands of hosts.
  • Hardware rate: FPGAs on the load module send at exact line rate, which a laptop running iPerf can't do.
  • Signature: each frame carries a stream ID, sequence number and timestamp. The receive port uses them to count loss, latency and reordering.

RFC 2544

The standard benchmark: for each frame size, find the highest rate with zero loss. Small frames are the hard case, because the switch has to make many more forwarding decisions per second.

Putting it together · every build

CI/CD on real hardware

The instruments above only pay off when they run automatically. Push a commit: Jenkins or GitLab builds it, a runner wired to the RF bench tests it on real devices, and it goes to staging before release. Run it a few times; benches fail in more than one way.

06
pick a scenario, or push for a random one
# waiting for a commit…
# .gitlab-ci.yml (simplified)
stages: [build, unit, rf_bench, staging, release]

rf_bench:
  stage: rf_bench
  tags: [rf-bench]   # runner wired to the chamber
  script:
    - python bench/check_path_loss.py --max-drift 1.0
    - python bench/flash_dut.py --build $CI_COMMIT_SHA
    - pytest tests/rf --atten 0:80:2 --junitxml=rf.xml
  artifacts:
    reports: { junit: rf.xml }

staging:
  stage: staging
  script: python deploy.py --env staging-hosts
  needs: [rf_bench]
